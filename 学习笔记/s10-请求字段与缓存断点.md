## 图一 · 同一个工具名出现两次，各自交付了什么？

沿教程 s10 走一遍。假设用户要读 `README.md` 前 20 行，项目的记忆索引里已有“金额使用整数分”。下面将提示文字意译成中文，保留协议字段。记忆索引出现在请求里，只说明模型可见它；这个读取任务用不上金额约定。

```text
第 1 次 API 请求
│
├─ system                         s10 把下列各段拼成一个字符串
│  ├─ 身份与行为                  你是编码助手，直接执行任务
│  ├─ 工具概览                    可用工具有 bash、read_file、write_file
│  ├─ 工作目录                    当前项目目录
│  └─ 记忆索引（文件非空时）      Relevant memories:
│                                 - [金额约定](money.md) — 金额使用整数分
│
├─ tools                          本次可调用工具的规格
│  ├─ bash                        …
│  ├─ read_file
│  │  ├─ name          = "read_file"
│  │  ├─ description   = "Read file contents."
│  │  └─ input_schema
│  │     ├─ type       = "object"
│  │     ├─ properties = {path: string, limit: integer}
│  │     └─ required   = ["path"]
│  └─ write_file                  …
│
└─ messages
   └─ user: "读 README.md 前 20 行"

模型返回       assistant.content 中出现 tool_use
               {id:"call_1", name:"read_file", input:{path:"README.md", limit:20}}
                         ↓
Harness 本地   用工具名找到 Python 函数，传入本次参数并读取文件
                         ↓
第 2 次请求    messages 保留用户问题，随后是两条新消息
               assistant → 上一轮响应，含上述 tool_use
               user      → [{type:"tool_result", tool_use_id:"call_1",
                             content:"……实际读到的 20 行……"}]
```

**盯住 `limit` 就能读懂这张图。** `system` 提及工具名，`tools[].description` 说明能读文件，`input_schema` 约定参数叫 `limit`、类型是整数、可以省略。具体数值 `20` 出现在这次调用的 `input`。实际文件内容随后进 `messages`，靠 `tool_use_id` 与原调用配对。[s10 提示词组装](https://github.com/shareAI-lab/learn-claude-code/blob/20e7cbb72c66ab01967299ad3eac6c7bda242136/s10_system_prompt/code.py#L42) · [工具规格与执行循环](https://github.com/shareAI-lab/learn-claude-code/blob/20e7cbb72c66ab01967299ad3eac6c7bda242136/s10_system_prompt/code.py#L134)

### “按需加载”要追到哪一栏？

| 机制 | 触发前模型看到什么 | 谁触发，触发后交付什么 |
|---|---|---|
| Skill · s07 | `system` 带技能目录，每项是名字和一句简介。`tools` 带 `load_skill(name)` 的规格。 | 模型请求加载技能，Harness 将 `SKILL.md` 全文作为 `tool_result.content` 追加到 `messages`。全文只加载一次，也能随历史在后续请求中多次可见。[目录](https://github.com/shareAI-lab/learn-claude-code/blob/20e7cbb72c66ab01967299ad3eac6c7bda242136/s07_skill_loading/code.py#L93) · [全文](https://github.com/shareAI-lab/learn-claude-code/blob/20e7cbb72c66ab01967299ad3eac6c7bda242136/s07_skill_loading/code.py#L269) |
| Memory · s09 | `system` 可带记忆索引，每项有名称、文件链接和简介。 | 用户回合开始时，Harness 主动选择相关条目，把命中文件的正文包入 `<relevant_memories>`，拼到请求副本的用户文本前面。它可以在本回合第一次模型调用时就可见。图一的 s10 只演示索引拼接；跟到 s09 才能看到逐文件召回。[s09 请求组装](https://github.com/shareAI-lab/learn-claude-code/blob/20e7cbb72c66ab01967299ad3eac6c7bda242136/s09_memory/code.py#L583) |

## 图二 · 同一条 SQL 任务怎样从请求字段走到缓存前缀？

假设用户问“按项目的 SQL 规范，检查账单金额”。这张图把 s07 的技能目录、s09 的记忆召回、s10 的提示组装放在一个教学例子里。为了演示缓存，在例子里把 `system` 分成两个 API 文本块，并设置断点。实际 s10 脚本发送一个字符串。

```text
本地资料                         Harness 组出的模型输入
──────────────────────────────────────────────────────────────
普通工具注册表             ───► T  = 顶层 tools 中预先加载的工具规格
                                    read_file、load_skill 的名称、描述、参数约束
身份、工具使用规则、技能目录 ───► S1 = system 的第一块
                                    编码助手；有 sql-style 技能，可按需加载
工作目录、当前记忆索引     ───► S2 = system 的第二块
                                    billing 项目；money.md 的索引条目
召回的 money.md + 用户任务 ───► U1 = user 消息
                                    金额以整数分存储……；按项目规范检查账单
模型决定加载 SQL 规范      ───► A1 = assistant 消息里的 tool_use
                                    id=call_1, name=load_skill, input={name:"sql-style"}
Harness 返回技能全文       ───► R1 = user 消息里的 tool_result
                                    tool_use_id=call_1, content="SQL 规范全文……"

API 按 tools → system → messages 的次序匹配前缀
──────────────────────────────────────────────────────────────
第 1 次   [ T ][ S1 ]◆[ S2 ][ U1 ]●
          ◆ A  所在前缀 = T + S1
          ● B1 所在前缀 = T + S1 + S2 + U1

第 2 次   [ T ][ S1 ]◆[ S2 ][ U1 ][ A1 ][ R1 ]●
          至 U1 仍与旧 B1 相同；本次末尾断点 B2 移到 R1 之后。
```

**回到当时最后的追问：`T` 是工具规格这块数据，`◆` 才是断点 A。** “固定”说的是这里选择一直在 S1 末尾标记。要判断能否命中旧 A，就把两次的 `T + S1` 整段拿来比较。S2 即使是运行时动态生成的，只要两次生成的实际内容相同，也可以随旧 B1 一起命中。[Anthropic 前缀与断点规则](https://platform.claude.com/docs/en/build-with-claude/prompt-caching#explicit-cache-breakpoints)

### 用四个改动自测

假设模型与其他缓存相关设置相同、满足最低缓存长度、旧 A 和 B1 均已写入且仍有效，旧断点也在查找范围内。每行都单独从图中第一次请求出发。

| 下一次改了什么 | 最长可复用到哪里 | 怎么判断 |
|---|---|---|
| 末尾追加 `load_skill` 调用和技能全文 | **B1** | 到 U1 的旧前缀完全相同，新内容从 A1 开始。若末尾跟随对话增长，还可以在 B2 写入更长的前缀。 |
| S2 的记忆索引从一条变成两条 | **A** | 到 S1 的前缀相同。旧 B1 包含旧索引，即便后面的用户问题逐字相同，也匹配不上旧 B1。 |
| 给原本就加载的 `read_file` **定义**新增参数 | **图里的旧 A、B1 都失配** | T 已变，两个断点都覆盖它。若只是调用已有的 `limit` 参数并填入 `20`，实参进入尾部的 `tool_use.input`，T 保持原值。 |
| 第一次只在 B1 写过缓存，随后更换 S2 | **图中没有可读的旧 A** | 前半段稳定只是条件之一。第一次还须在 A 处实际写入过缓存，下一次才有这一项可读。 |

**关于延迟工具的一处更正。** 先前把“下一次 HTTP 请求的 `tools` 数组多了一项”直接推成“最左侧的 T 变了”，混淆了客户端发包和服务端构造缓存前缀。上表第三行说的是改动**预先加载**的工具定义。按 Anthropic 对 `defer_loading: true` 的说明，工具发现后通过历史中的 `tool_reference` 展开，先前的普通工具前缀可以继续复用。若与此同时改写了前面的目录消息或其他已缓存内容，仍要从实际改动的位置重新判断。[Anthropic：延迟加载与缓存保留](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching#defer_loading-and-cache-preservation)

### 在源码和响应里分别看什么？

| 想确认的事 | 能回答它的证据 |

| s10 这次有没有重新拼接 `system`？ | 看 `get_system_prompt(context)`。它序列化 `context` 作为本地键，键相同就取上次的字符串并打印 `[cache hit]`。主循环仍照常发送请求；这个脚本没有显式设置图二的 A、B。[本地缓存](https://github.com/shareAI-lab/learn-claude-code/blob/20e7cbb72c66ab01967299ad3eac6c7bda242136/s10_system_prompt/code.py#L71) · [实际发包](https://github.com/shareAI-lab/learn-claude-code/blob/20e7cbb72c66ab01967299ad3eac6c7bda242136/s10_system_prompt/code.py#L172) |
